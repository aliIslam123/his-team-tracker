# Holool His

نظام داخلي لمتابعة تسجيل العاملين في نظام معلومات المستشفى (HIS): فريق الدعم يقيّم كل محاولة تسجيل من نموذج بسيط على الموبايل، والمشرفون يتابعون النقاط والمتابعات والتصعيدات من لوحة التحكم.

Internal tool for tracking staff registration on the hospital HIS. Field team members submit evaluations from a mobile-friendly public form; supervisors follow scores, follow-ups and escalations from the dashboard.

## كيف يعمل (How it works)

| الصفحة | الوظيفة |
| --- | --- |
| `/h/<slug>` | نموذج التقييم العام لكل مستشفى (بدون تسجيل دخول): اختيار الموظف ← نتيجة المحاولة ← ملاحظات ← متابعة |
| `/login` | تسجيل دخول المهندسين باسم المستخدم وكلمة المرور (الحسابات ينشئها الأدمن فقط) |
| `/change-password` | تغيير كلمة المرور (إلزامي عند أول دخول أو بعد إعادة تعيين) |
| `/dashboard` | أرقام عامة، من يحتاج انتباهًا، متابعات قادمة، تصعيدات، آخر التقييمات |
| `/admin/hospitals` | إدارة المستشفيات (super_admin): إضافة/تعديل/إيقاف + رابط النموذج العام |
| `/admin/users` | إدارة الحسابات داخل كل مستشفى: إنشاء/دور/صلاحيات/إيقاف/إعادة تعيين كلمة المرور |
| `/admin/comparison` | مقارنة المستشفيات جنب بعض (super_admin): الموظفون، التقييمات، المتابعات، التصعيدات |
| `/staff`, `/staff/[id]` | دليل الموظفين، الملف الشخصي، التعديل، تصفير النقاط، تصدير Excel |
| `/history` | كل التقييمات مع فلاتر وتصدير |
| `/followups` | المتابعات المجدولة (مفتوحة / متأخرة / مكتملة) |
| `/escalations`, `/escalations/[id]` | مراجعة التصعيدات واعتماد الخطاب وطباعته |
| `/analytics` | رسوم بيانية (حسب الوظيفة، الحالة، الأشهر، الأقسام، النتائج) |
| `/import` | استيراد الموظفين من CSV/Excel مع كشف التكرار |
| `/activity` | سجل النشاط (للمدير/المشرف) |
| `/notifications`, `/settings` | الإشعارات (المدير/المشرف يرسل لكل المستشفيات أو مستشفى بعينه أو شخص/أشخاص محددين) والإعدادات |

### مستشفيات متعددة (Multi-hospital)

- كل مستشفى له **رابط عام خاص** بنموذج تقييمه: `/h/<slug>` (مثل `/h/ain-shams`)، والدوال العامة في قاعدة البيانات محدودة بمستشفى الـ slug نفسه.
- كل بيانات المستشفى (الموظفون، التقييمات، المتابعات، التصعيدات، الأسرّة، السجل) معزولة على مستوى قاعدة البيانات بـ **RLS**: أي مستخدم يرى مستشفاه فقط — لا في الواجهة ولا في الـ API ولا في عناوين URL.
- **super_admin** يرى كل المستشفيات (مبدّل مستشفى في الشريط العلوي) وينشئها من `/admin/hospitals`.
- الأقسام تبقى عامة ومشتركة بين المستشفيات.
- عند أول تشغيل لـ `0005` تُنقل البيانات الحالية كلها إلى أول مستشفى «عين شمس» (`slug: ain-shams`).

### الصلاحيات (Permissions — المرحلة 2)

- **مصدر واحد** لكل صلاحيات النظام: `src/lib/permissions.ts` في الواجهة، ودالة `public.has_permission()` في `supabase/migrations/0006_permissions.sql` في قاعدة البيانات. القائمتان متطابقتان بالضرورة.
- الأدوار تحدد الـ **افتراضيات**: `super_admin` = الكل، `hospital_admin` = كل شيء عدا إدارة المستشفيات والمقارنة، `supervisor` = إدارة الموظفين/الاستيراد/المراجعات/المتابعات + **إنشاء حسابات أعضاء فريق (`member`) داخل مستشفاه فقط** (بدون تعديل/إعادة تعيين كلمات المرور أو منح أدوار أعلى)، `member` = لوحة التحليلات + تعديل الأسرّة المسندة له.
- أي صلاحية قابلة للتعطيل/التفعيل **لكل مستخدم** من `/admin/users` (تعديل → «صلاحيات إضافية»): التبديلات تُحفظ كـ overrides في `profiles.permissions` وتفرضها الـ RLS نفسها — وليس مجرد إخفاء أزرار.
- `hospitals.manage` و`comparison.view` مفتاحان **للـ super_admin فقط دائمًا** ولا يمكن تفعيلهما لدور أدنى عبر أي override.
- **إسناد الموظفين**: كل موظف له «المهندس المسؤول» (`assigned_to`) — يُحدد من شاشة تعديل الموظف (حسابات member فقط، ومن نفس المستشفى).
- **عزل سجل التقييمات للعضو**: كل عضو يرى فقط التقييمات التي سجّلها هو (`recorded_by`) **+** تقييمات الموظفين المسندين إليه. باقي الأدوار ترى مستشفى كاملًا.

### قواعد النقاط (Scoring)

- نتيجة إيجابية (+1): تم التسجيل، تعاون، قبل التدريب، أكمل الخطوات.
- نتيجة سلبية (−1): رفض، قال مشغول ورفض تحديد وقت، أجّل مرارًا، رفض المساعدة، غادر دون إكمال.
- محايدة (0): انشغال طبي، حالة طارئة، مشكلة نظام، تأخير إداري… إلخ.
- عندما يصل **صافي النقاط إلى −3 أو أقل** يُفتح تصعيد تلقائيًا ويصل إشعار للمدير/المشرفين.
- القواعد معرّفة في مكان واحد: `src/lib/evaluation.ts` (ويُطبقها الخادم في دالة `submit_evaluation` داخل `0002_integration.sql`، فلا يمكن تزوير النقاط من المتصفح).

## وضعان للتشغيل (Two modes)

1. **Demo** (الافتراضي عند عدم ضبط Supabase): كل البيانات في `localStorage` للمتصفح الحالي فقط، ولا تُشارَك مع أجهزة أخرى. مناسب للتجربة.
   الدخول من `/login` بحساب الديمو (يمكن تغييره بـ `NEXT_PUBLIC_DEMO_USER` / `NEXT_PUBLIC_DEMO_PASSWORD`).
2. **Live** (Supabase): قاعدة بيانات مشتركة + Supabase Auth + صلاحيات (RLS). هذا هو الوضع المطلوب للاستخدام الفعلي من عدة أجهزة.

### إعداد Supabase

1. أنشئ مشروعًا، وفي **SQL Editor** شغّل بهذا الترتيب:
   1. `supabase/migrations/0001_init.sql`
   2. `supabase/migrations/0002_integration.sql`  ← دوال النموذج + إصلاحات أمنية
   3. `supabase/migrations/0004_bed_followups.sql`  ← متابعة الأسرّة (`/beds`)
   4. `supabase/migrations/0005_hospitals.sql`  ← **مستشفيات متعددة + حسابات بلا تسجيل ذاتي + RLS معزول**
   5. `supabase/migrations/0006_permissions.sql`  ← **نظام صلاحيات موحد + إسناد الموظفين + عزل سجل العضو + مقارنة المستشفيات**
   6. `supabase/migrations/0008_notifications.sql`  ← **إرسال الإشعارات من المشرف/المدير + تأمين RLS**
   7. `supabase/migrations/0009_production_hardening.sql`  ← **أرقام الأسرّة فريدة لكل مستشفى + صلاحيات الأسرّة + حماية النموذج العام من السبام**
   8. `supabase/migrations/0010_comparison_beds.sql`  ← **عدد متابعات الأسرّة والأسرّة التي تحتاج متابعة في مقارنة المستشفيات**
   9. `supabase/migrations/0011_comparison_team.sql`  ← **«فريق العمل» من الحسابات، و«السراير» و«بانتظار المهندس» من متابعة الأسرّة**
   10. `supabase/migrations/0012_comparison_patients.sql`  ← **«مسجل» و«بالانتظار» بقى فيه عدد المرضى المسجّلين/المنتظرين على الأسرّة**
   11. `supabase/seed.sql` (الأقسام)
   12. `supabase/seed_staff.sql` (قائمة الموظفين — يربطهم تلقائيًا بمستشفى «عين شمس»)

   > لا يوجد migration برقم `0007` عمدًا (ربط الأسرّة بحساب المهندس مرحلة مؤجلة). التسلسل ليس خطأ.
2. **اقفل التسجيل الذاتي**: من لوحة Supabase → **Authentication → Providers → Email** أطفئ **Enable Sign-ups** (بذلك لا يمكن لأحد إنشاء حساب بنفسه؛ الحسابات تُنشأ من شاشة الأدمن فقط).
3. أنشئ أول **super_admin** من **Authentication → Users** (أو دعه ينشأ من شاشة الأدمن لاحقًا)، ثم اربطه بالدور والمستشفى:
   ```sql
   -- المستشفى الأول موجود بالفعل بعد 0005 باسم «عين شمس» (slug: ain-shams)
   update public.profiles
      set role = 'super_admin', username = 'admin', hospital_id = null
    where email = 'you@example.com';
   ```
   الأدوار: `super_admin` (كل المستشفيات) · `hospital_admin` (كل صلاحيات مستشفاه) · `supervisor` (تعديل واعتماد تصعيدات واستيراد + إضافة مهندسين `member` في مستشفاه فقط) · `member` (تقييمات ومتابعاته).
4. ضع `NEXT_PUBLIC_SUPABASE_URL` و`NEXT_PUBLIC_SUPABASE_ANON_KEY` في `.env.local` (وفي Vercel)، وضع أيضًا `SUPABASE_SERVICE_ROLE_KEY` (سيرفر فقط — بدون `NEXT_PUBLIC_`) لأن شاشات إدارة الحسابات تعمل من خلاله.
5. شارك مع كل مستشفى رابط نموذجها: `https://<domain>/h/<slug>` (يظهر بزر نسخ في `/admin/hospitals`).

## متابعة الأسرّة (`/beds`)

بديل شيت جوجل/إكسيل: كل سرير في صف، وبجانبه خانات مهام الأطباء والتمريض. اضغط الخانة لتحديدها (تُحفظ فورًا ويراها الجميع خلال ٣٠ ثانية)، مع تاريخ آخر تعديل للأطباء وللتمريض (يتلوّن بالأخضر لو اليوم وبالبرتقالي لو قديم).

- **الاستيراد**: زر «استيراد من الشيت» (للمدير/المشرف) يقرأ نفس أعمدة الشيت الحالي (`.xlsx` أو `.csv`) ويعرض معاينة قبل الحفظ. الأسرّة الموجودة (نفس المكان + رقم السرير) تُستبدل بياناتها.
- **التصدير**: زر «تصدير Excel» بنفس ترتيب أعمدة الشيت، ويمكن إعادة استيراده.
- **تغيير الأعمدة**: قائمة المهام ومجموعتها (أطباء/تمريض) في مكان واحد: `BED_TASKS` داخل `src/lib/beds.ts`. لا تحتاج تعديل قاعدة البيانات (لا تغيّر `key` بعد وجود بيانات).
- **خروج مريض**: زر «تفريغ السرير» يمسح الاسم والملاحظات والتواريخ والعلامات ويُبقي السرير.
- **الخصوصية**: هذه بيانات مرضى. استخدم وضع Live (Supabase مع تسجيل دخول) ولا تضع أسماء حقيقية في وضع Demo على موقع عام. سجل النشاط يسجّل إنشاء/تفريغ/حذف/استيراد الأسرّة **دون** أسماء المرضى.

## الأمان

- مفتاح `SUPABASE_SERVICE_ROLE_KEY` **سيرفر فقط** (متغير بيئة عادي بدون `NEXT_PUBLIC_` ولا يظهر في أي حزمة متصفح) ويُستخدم حصرًا في Route Handlers إدارة الحسابات (`/api/admin/users`). كلمات المرور تُخزَّن مشفّرة في Supabase Auth ولا تُخزَّن أو تُشفَّر في المشروع، وتظهر للأدمن **مرة واحدة** عند الإنشاء/الإعادة.
- لا تضع `service_role` key في المتصفح أو في الكود أبدًا.
- نموذج التقييم العام لا يملك صلاحية مباشرة على الجداول؛ يعمل فقط عبر دوال SQL محدودة **بمستشفى الـ slug** (`search_staff_h`, `add_staff_public_h`, `submit_evaluation_h`, `public_stats_h`)، والدوال القديمة العامة ملغاة (`revoke`) عن `anon` و`authenticated`.
- العزل على مستوى قاعدة البيانات بـ RLS: مستخدم المستشفى A لا يقرأ ولا يعدّل أي صف لمستشفى B (بما فيها صف المستشفى نفسه). اختبارات القبول: `supabase/tests/0005_rls_tests.sql` (مستشفيان + كل السيناريوهات داخل معاملة واحدة تتراجع عند أي فشل).
- المستخدم لا يستطيع تغيير دوره أو مستشفاه أو صلاحياته أو اسم مستخدمه بنفسه (trigger على `profiles` + لا يوجد أي INSERT policy على `profiles`).
- سجل النشاط للإضافة فقط (لا تعديل ولا حذف)، وتصفير النقاط يحتفظ بالسجل، و**بدون** أسماء مرضى أو كلمات مرور.
- أعمدة كلمات المرور وPIN والرقم القومي والهاتف والراتب لا تُقرأ ولا تُحفظ عند الاستيراد.
- بيانات الديمو داخل المتصفح غير محمية؛ لا تضع بيانات حقيقية في وضع Demo على موقع عام.


## النشر على بيئة العمل (Production go-live)

### 1) قبل النشر (مرة واحدة)

1. شغّل الـ migrations بالترتيب أعلاه، ثم اختبارات `supabase/tests/*.sql` على **مشروع Supabase تجريبي منفصل** (وليس على مشروع الإنتاج) وتأكد أن كلها PASS.
2. أطفئ **Enable Sign-ups** (Authentication → Providers → Email) وأطفئ أي Provider غير مستخدم.
3. أنشئ أول `super_admin` بالـ SQL الموجود أعلاه، وأعطه كلمة مرور قوية، وغيّرها من `/settings`.
4. فعّل **Backups**: خطة Supabase المجانية **لا تحتفظ بنسخ احتياطية تلقائية** يمكن الاسترجاع منها؛ لبيانات حقيقية إما الترقية لخطة بها PITR/Daily Backups أو جدول `pg_dump` دوري (أسبوعيًا على الأقل) محفوظ خارج Supabase.
5. المشروع المجاني على Supabase **يتوقف بعد أسبوع من عدم النشاط**؛ للاستخدام اليومي هذا غير مؤثر، لكن اضبط مراقبة (الخطوة 4).

### 2) متغيرات البيئة على Vercel (Production فقط)

| المتغير | ملاحظة |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | من Project Settings → API |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | المفتاح العام `anon` |
| `SUPABASE_SERVICE_ROLE_KEY` | **سري — سيرفر فقط**، بدون `NEXT_PUBLIC_`. لا يوضع في Preview deployments العامة |
| `NEXT_PUBLIC_ALLOW_DEMO` | **لا تضعه** في الإنتاج |

> في الإنتاج لو نسيت متغيرات Supabase، الموقع **يتوقف برسالة واضحة** ولا يعمل بوضع Demo (حتى لا يُكشف حساب التجربة). هذا مقصود.
> ملاحظة: متغيرات `NEXT_PUBLIC_*` تُدمج وقت الـ build، فبعد تغييرها اعمل **Redeploy**.

### 3) إعدادات Supabase Auth الموصى بها

- Authentication → Rate Limits: اترك الحدود الافتراضية أو شددها (محاولات الدخول مقيدة من Supabase نفسه).
- Password strength: أقل طول 8 (الأدمن يولّد كلمات مرور من 16 حرفًا).
- URL Configuration → Site URL = رابط الموقع الفعلي.

### 4) المراقبة

- `GET /api/health` يعيد `200` لو الموقع وقاعدة البيانات شغالين و`503` لو القاعدة لا ترد (لا يكشف أي بيانات). اربطه بـ UptimeRobot أو Better Stack كل 5 دقائق.

### 5) قائمة فحص بعد النشر

- [ ] `https://<domain>/h/ain-shams` يفتح من موبايل بدون تسجيل دخول ويقبل تقييمًا تجريبيًا.
- [ ] `/login` يرفض كلمة مرور خاطئة، ويقبل الأدمن.
- [ ] إنشاء مهندس من `/admin/users` يعرض كلمة المرور مرة واحدة، وتسجيل دخوله يطلب تغييرها.
- [ ] مهندس `member` لا يرى `/admin/users` ولا `/activity`، ولا يستطيع حذف سرير.
- [ ] مستشفى ثانية: مستخدمها لا يرى بيانات «عين شمس».
- [ ] تعطيل حساب يمنعه من الدخول فعلًا.
- [ ] `https://<domain>/api/health` يعيد `{"status":"ok"}`.
- [ ] احذف حساب/بيانات أي اختبار تجريبي قبل التسليم.

### 6) ما يجب معرفته (حدود حالية)

- **ربط الأسرّة بحساب المهندس غير منفّذ بعد**: صلاحية `beds.assigned` تسمح للعضو بتعديل أسرّة **مستشفاه** (وليس فقط المسندة له)، لأن المالك ما زال اسمًا نصيًا `owner_name`. إن كان هذا غير مقبول لبياناتكم فأجّل إعطاء الأعضاء صلاحية الأسرّة (`beds.assigned = false` من `/admin/users`) إلى حين تنفيذ مرحلة الربط.
- **حدود السبام**: النموذج العام يقبل 200 تقييم/5 دقائق و40 موظفًا جديدًا/10 دقائق لكل مستشفى. غيّر الأرقام في `0009` لو لزم. الرابط العام نفسه بلا تسجيل دخول بالتصميم، فلا تشاركه إلا مع الفريق.
